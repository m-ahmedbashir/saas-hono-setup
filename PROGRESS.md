- WS origin validation on `/ws/:userId` (`apps/api/src/modules/notifications/notifications.routes.ts`): rejects the handshake (403) unless the `Origin` header is in `ALLOWED_ORIGINS` (shared via `apps/api/src/lib/allowed-origins.ts`, also used by the Hono CORS middleware in `app.ts`). Closes a cross-site WebSocket hijacking gap identified by `/security-review`: WS handshakes aren't subject to CORS the way `fetch` is, so without this check the only thing preventing a cross-site page from opening a socket (cookies attach regardless of origin) was Better Auth's session cookie defaulting to `SameSite=Lax` — a client-side default, not a server-side control, and one this repo is explicitly likely to need to change (`sameSite: "none"`) once frontend and API live on separate domains, which is the normal SaaS deployment shape. Verified with a real integration test: a request with a valid session, matching `:userId`, but a disallowed `Origin` gets rejected.
- Row-Level Security on both `organization_billing` and `individual_billing`, as a defense-in-depth layer on top of (not instead of) the existing app-level auth/permission checks. `withOrgScope`/`withUserScope`/`withSystemScope` helpers (`packages/db/src/index.ts`); both `.db.ts` files take an explicit `tx: DbExecutor` instead of the bare `db` client. **Found and fixed a real, easy-to-miss gap while building this**: the app's DB connection role (Neon's default owner role, `neondb_owner`) has `BYPASSRLS` granted directly on the role — confirmed via `pg_roles.rolbypassrls`, not assumed — which means `ENABLE`/`FORCE ROW LEVEL SECURITY` alone did nothing for our own app's queries; a table-owner-exemption fix (`FORCE`) doesn't touch a role-level `BYPASSRLS` grant. Fixed by creating a second, restricted `app_user` role (`packages/db/scripts/create-app-role.js`, no `BYPASSRLS`) that the app now connects as for all runtime queries via a new `APP_DATABASE_URL` env var — `DATABASE_URL` (owner) is now used only for migrations. `packages/db/src/index.ts` throws at import time if `APP_DATABASE_URL` is unset rather than silently falling back to the bypassing owner role. CI's ephemeral test Postgres got the same treatment (a `postgres:16` Docker image's default role is also a superuser, same bypass problem) — see `.github/workflows/ci.yml`. Verified with real tests, not just by reading the migrations: both integration test files' "Row-Level Security" describe blocks prove an unscoped query and a wrong-owner-scoped query both see zero rows, and the right owner's scope sees the row — this caught the `BYPASSRLS` gap on its first run (failed, correctly) before the role fix, and passes now. The `create-app-role.js` default-privileges grant was also confirmed working for real (not just assumed) when `individual_billing` was added later and needed zero manual re-grant.

- Route handler discipline tightened: every route handler is now a named function in a `<feature>.controller.ts`, referenced by name from `.routes.ts` — no inline handler bodies at all, even trivial ones (previously "one call, respond" was allowed inline; see `AGENTS.md`'s rewritten rule). - User profile — `profile` table (`packages/db/src/schema.ts`), FK'd to `user.id`, RLS-enabled via `withUserScope` (same pattern/rigor as the billing tables — see `AGENTS.md`'s User Profile section). `phone`, `dateOfBirth` (not a raw `age` — goes stale; bounded not-future/not->130-years in `profile.schema.ts`), and a structured address (`addressStreet`/`addressCity`/`addressState`/`addressPostalCode`/`addressCountry`, `addressCountry` validated as ISO 3166-1 alpha-2). `GET`/`PATCH /profile` (`profile.routes.ts` → `profile.controller.ts` → `profile.service.ts` → `profile.db.ts`, following the tightened route-handler-discipline rule from the start), ownership-scoped only (no `requirePermission`/org concept — same reasoning as individual billing, works for B2C and B2B2C identically). `PATCH` is a real partial update: an omitted field means "leave unchanged," an explicit `null` means "clear it," verified by a dedicated test, not just implemented and assumed. Profile row is created lazily on first `PATCH`, not at signup. `profile.integration.test.ts`, 8 tests: auth gate, lazy-creation default (all-null) shape, three validation-rejection cases (malformed body, non-ISO country, future `dateOfBirth`), partial-update-preserves-other-fields, explicit-null-clears-field, and the RLS proof block (unscoped/wrong-user/right-user).
- `DELETE /account` — permanent, self-service account deletion (`apps/api/src/modules/account/`). Blocks (422) if the caller is the sole `"owner"` of an org with other members (no silent orphaning); deletes a solo-owned org (with no other members) along with the account instead of leaving it permanently orphaned. Calls `billingService.cancelSubscription` best-effort for any live Stripe subscription before deleting DB rows — its first real caller, since it was implemented earlier but never routed. Deletes `user`/`organization` directly and lets `ON DELETE CASCADE` clean up everything FK'd to them (`profile`, `individual_billing`, `organization_billing`, `organization_profile`, `session`, `account`, `member`, `invitation`) — cascade actions are not subject to Row-Level Security, confirmed empirically against the real database (see `AGENTS.md`'s "Account deletion" section for how, and its correction of an earlier wrong claim here that cascade gets blocked by RLS — that claim shipped without being checked against the actual database, and wasn't true). Reading each RLS-protected child's `providerSubscriptionId` before the parent delete (via `withOrgScope`/`withUserScope`) is still required — not to delete the row, but because it's needed for the Stripe cancellation call and won't exist to read afterward. Added `AnyExecutor` (`packages/db/src/index.ts`) for the few queries here against non-RLS tables (`member`/`organization`/`user`) where a plain `db` client is fine but the stricter `DbExecutor` type would otherwise force scoping that doesn't apply. `account.integration.test.ts`, 5 tests: auth gate, solo-user deletion, solo-owned-org-cascade-deletion (including its billing row), the sole-owner-with-other-members block (and that nothing was deleted), and a non-owner member's own deletion leaving the org and other members untouched.
- Organization profile — `organization_profile` table (`packages/db/src/schema.ts`), FK'd to `organization.id`, RLS-enabled. `orgNumber` (permanent, human-friendly, unique, indexed 8-char code, ambiguous-character-free alphabet, `randomInt`-generated) plus industry/`companySize`/website/phone/`taxId`/description/structured address. The one real deviation from every other table in this repo: created **eagerly**, via a real, verified Better Auth `organizationHooks.afterCreateOrganization` hook (`packages/core/src/auth/index.ts`) — checked the installed `better-auth@1.6.23`'s actual `.d.mts` for this before relying on it, not assumed. `ensureOrganizationProfileRow` (`packages/db/src/organization-profile.ts`, not `packages/core` — would be a circular workspace dependency, see AGENTS.md) is called both by the hook (eager) and by the routes (defensive, idempotent — backfills pre-existing orgs). Its collision-retry runs each insert attempt inside a real `tx.transaction(...)` **savepoint**, not directly on the caller's `tx` — verified against drizzle-orm's actual `NodePgTransaction` source that this issues `SAVEPOINT`/`ROLLBACK TO SAVEPOINT` rather than aborting the whole outer transaction, which a raw retry-on-same-tx would have hit (Postgres aborts an entire transaction after any failed statement until rolled back). After a collision it re-checks by `organizationId` before regenerating, so a genuine `orgNumber` collision and a concurrent caller's race are handled differently instead of conflated. `GET /organization-profile` — any member; `PATCH` — owner/admin only via a new `organizationProfile: ["manage"]` permission (`packages/core/src/auth/permissions.ts`), not billing's. `orgNumber` isn't in the update schema at all, so a client attempt to set it is silently stripped by Zod. Deliberately documented as NOT a future join-code candidate — see AGENTS.md's reasoning. `organization-profile.integration.test.ts`, 7 tests, including one that reads the profile immediately after org creation with no prior access, specifically to prove the eager hook actually fired rather than trusting it silently.
- Production hardening from a load-focused audit (a mix of a self-review and a second AI's independent pass, cross-checked against the actual code before acting on any of it) — see `AGENTS.md`'s "Production hardening" section for the full reasoning on each. Postgres pool `max`/timeouts made explicit and env-driven (`DB_POOL_MAX`/`DB_POOL_IDLE_TIMEOUT_MS`/`DB_POOL_CONNECTION_TIMEOUT_MS`) instead of node-postgres's wrong-for-production defaults (`max: 10`, wait-forever `connectionTimeoutMillis`), plus a `pool.on("error", ...)` handler (an unhandled error on an idle pooled client otherwise crashes the whole process). Graceful shutdown on `SIGTERM`/`SIGINT` (`apps/api/src/lib/graceful-shutdown.ts`) — drains in-flight requests and closes the DB pool before exit, with a 10s force-exit fallback since `server.close()` doesn't proactively close already-upgraded WebSocket connections. **Found and fixed a real correctness bug, not just a scale one**: the WebSocket dispatcher (`websocket-dispatcher.ts`) used `Map<string, WSContext>` — a second connection for the same user (a second tab/device) silently overwrote the first's registration, and closing the _first_ connection then deleted the _second_'s still-open entry, leaving a live socket that would never receive anything again. Reproduces with one user and two tabs, nothing to do with 100k users. Fixed with `Map<string, Set<WSContext>>` and a `NotificationDispatcher.removeClient` signature change (now takes the specific client, not just `userId`) — regression-tested directly (`websocket.integration.test.ts`: two connections, close the first, assert the second still receives a message). Stripe checkout creation now accepts an optional caller-supplied `Idempotency-Key` header, passed through to `BillingGateway.createCheckoutSession`/`createIndividualCheckoutSession` — checked the installed Stripe SDK's actual source first and confirmed its own auto-generated per-call key only protects the SDK's internal network-retry, not a retried HTTP request to our own API, so a server-generated key would have added nothing real.
- **Corrected a wrong claim shipped earlier in this same session, caught while building the next feature — not by a separate review.** While reasoning through a new "delete organization" feature, noticed `account.service.ts` never explicitly deleted `organization_profile` (added after that code was written) before deleting `organization`, yet its test still passed — which shouldn't have been possible under the earlier-documented understanding that RLS blocks unscoped cascade deletes. Verified directly against the real database (created an org with an RLS-protected `organization_profile` row, deleted its parent `organization` row via the fully unscoped bare `db` client) and confirmed: **`ON DELETE CASCADE` is not subject to Row-Level Security in Postgres at all**, even with `FORCE ROW LEVEL SECURITY`. The original account-deletion "fix" and its documentation (`AGENTS.md`, this file) both shipped that wrong claim without empirically checking it — corrected both, and simplified `account.service.ts`/`account.db.ts` to remove the now-provably-unnecessary explicit pre-deletes (re-ran `account.integration.test.ts` after the simplification: still 5/5, confirming cascade alone was always sufficient). The one thing still genuinely required before deleting a parent row is reading each RLS-protected child's `providerSubscriptionId` for the pre-delete Stripe cancellation call — not deleting it, just reading it while it still exists.
- `DELETE /organization` — permanently deletes the caller's active organization: billing, profile, memberships, pending invitations. Owner-only (new `organization: ["delete"]` permission, not granted to `admin`). Built using the corrected cascade understanding above — no explicit pre-deletes needed, just cancel the Stripe subscription (best-effort) then delete the `organization` row. **The actual point of this feature, proven directly, not assumed**: deleting an org never touches any member's own account (`user`/`profile`/`individual_billing`) — GDPR's right to erasure belongs to each individual data subject, not to whatever org they belong to, so an org owner deleting the org has no bearing on a member's own personal data, only their membership in it. `organization.integration.test.ts` deletes an org with a non-owner member present and asserts both the owner's and the member's `user` rows survive. Deliberately has no "block if other members exist" guard (unlike `DELETE /account`'s org-deletion path) — this is an explicit, deliberate action by the owner, not a side effect of something else, so there's nothing to silently protect against. `deleteAccount`'s own solo-owned-org deletion now calls this same `organization.service.ts` function instead of duplicating it.

## Bugs found and fixed along the way (worth knowing so they aren't reintroduced)

- Passing a custom `roles` map to Better Auth's `organization` plugin **replaces** its defaults rather than merging — since only `member`/`admin` were defined, every org's auto-assigned `owner` (its creator) had _zero_ permissions until `ownerRole` was added explicitly.
- `betterAuth()` had no `trustedOrigins`, so it rejected requests from origins the Hono CORS middleware was already allowing — two separate checks. `trustedOrigins` now reads the same `ALLOWED_ORIGINS` env var as the CORS middleware, so they can't drift apart.
- `NODE_ENV=<mode>` lines inside `.env.*` files were dead weight once `cross-env` was introduced (`cross-env` sets it before `--env-file` would even load, and `--env-file` never overrides an already-set var) — removed, including deleting the then-empty `.env.production`.

## Removed — deliberately deferred, not lost

`packages/core/src/algorithms/` (BKT scoring stub) and `packages/core/src/ai/*` (agent types, Claude client, an `exercise-generator` agent, registry) were built early, then deleted. Decision: the SaaS foundation (auth, permissions, response contract) should be product-agnostic and reusable first; product-specific logic (AI agents, education-specific algorithms) comes later, designed against real requirements instead of speculatively. Also removed: the `@anthropic-ai/sdk` dependency from `packages/core/package.json` (nothing used it anymore) and the `"./ai"` export from that package's `exports` map. `packages/core/src/index.ts` no longer re-exports either. Confirmed via `pnpm install` + typecheck across all packages after removal — nothing else referenced them.

If/when this comes back: don't recreate the old structure from memory — redesign it against whatever the actual product requirement is at that point. The old `AIAgent<TInput, TOutput>` contract + registry pattern is a reasonable starting reference but isn't gospel.
