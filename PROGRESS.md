## Implemented and verified working

- Monorepo scaffold: `package.json`, `pnpm-workspace.yaml`, `turbo.json`, `tsconfig.base.json`.
- `packages/db`: Drizzle client + full Better Auth schema (`user`, `session`, `account`, `verification`, `organization`, `member`, `invitation`) generated via `@better-auth/cli generate` from the real auth config, not hand-written. Migrated onto a real Neon Postgres instance (`DATABASE_URL` in `.env.development`).
- `packages/core/src/auth`: Better Auth instance with `emailAndPassword` enabled and the Organization plugin, using `drizzleAdapter(db, { provider: "pg", schema })` pointed at `@repo/db`'s schema.
- `apps/api`: Hono server boots with the security/CORS/body-limit/etag middleware chain, serves `GET /health`, mounts Better Auth's handler at `/api/auth/**`.
- Sign-up and sign-in confirmed working end-to-end against the real DB — `POST /api/auth/sign-up/email` and `POST /api/auth/sign-in/email` both tested with curl, wrote/read a real row in Neon, returned a valid session cookie.
- `apps/api/src/middleware/auth.middleware.ts`: resolves session → B2C vs B2B2C `userContext`, reading the actual member role from `activeOrg.members`.
- `apps/api/src/middleware/permission.middleware.ts`: `requirePermission(permissions)` — PBAC gate for routes. B2B2C calls Better Auth's `auth.api.hasPermission` against the caller's org role; B2C passes through by design.
- `packages/core/src/auth/permissions.ts`: `statement` (resources → actions) is the permission source of truth; `ownerRole`/`adminRole`/`memberRole` are named bundles of it, registered as `{ owner, admin, member }` in the organization plugin config.
- The full B2C and B2B2C auth + permission paths are confirmed working end-to-end against the real DB, not just typechecked: sign-up, sign-in, org creation (creator → `owner` role), server-side `addMember` (→ `member` role), `hasPermission` correctly allowing an owner and a permitted member while blocking one without the right permission, B2C bypass, and an unauthenticated request correctly getting 401. Verified via a throwaway test harness, deleted afterward; all test data cleaned from Neon.
- Response envelope + centralized error handling (`packages/core/src/errors.ts`, `apps/api/src/lib/response.ts`, `app.onError` in `apps/api/src/app.ts`) — verified in both `NODE_ENV=development` (details/stack included) and `NODE_ENV=production` (suppressed) by actually booting and diffing responses, not just reading the code.
- `NODE_ENV`-driven environment detection: `cross-env` in each `apps/api` script sets it per-command (`dev`/`start`/`test`), verified by booting under each mode.
- `apps/api/src/app.ts` / `src/index.ts` split: `app.ts` builds and exports the Hono `app` (all middleware, routes, `onError`) with no side effects; `index.ts` is just the process entrypoint (`serve()` + `injectWebSocket()`). Done specifically to make the app importable from tests without booting a real server as a side effect.
- WebSocket notification dispatcher — `GET /ws/:userId` (`apps/api/src/modules/notifications/notifications.routes.ts`), backed by `HonoWebSocketNotificationDispatcher` (`.../websocket-dispatcher.ts`) implementing the `NotificationDispatcher<TClient>` interface from `packages/core/src/notifications/types.ts`. Auth guardrail rejects (403, before the WS handshake completes) any connection where the authenticated session's user doesn't match the `:userId` path param. Verified end-to-end with a real `ws` client against the real DB: wrong `userId` → rejected; matching `userId` → connects and receives a real message triggered via `notificationDispatcher.send()`. This is also the concrete reference example for the DDD/DIP interface-in-core / implementation-in-apps/api split described in `AGENTS.md`.
- WS origin validation on `/ws/:userId` (`apps/api/src/modules/notifications/notifications.routes.ts`): rejects the handshake (403) unless the `Origin` header is in `ALLOWED_ORIGINS` (shared via `apps/api/src/lib/allowed-origins.ts`, also used by the Hono CORS middleware in `app.ts`). Closes a cross-site WebSocket hijacking gap identified by `/security-review`: WS handshakes aren't subject to CORS the way `fetch` is, so without this check the only thing preventing a cross-site page from opening a socket (cookies attach regardless of origin) was Better Auth's session cookie defaulting to `SameSite=Lax` — a client-side default, not a server-side control, and one this repo is explicitly likely to need to change (`sameSite: "none"`) once frontend and API live on separate domains, which is the normal SaaS deployment shape. Verified with a real integration test: a request with a valid session, matching `:userId`, but a disallowed `Origin` gets rejected.
- Sentry production error monitoring: `apps/api/src/instrument.ts` calls `Sentry.init()` from `@sentry/hono/node`, guarded by `SENTRY_DSN` being set (no-op otherwise, so local dev without a DSN is unaffected). Imported as the first line of `src/index.ts` (before `@hono/node-server`/`app` are imported) so Sentry's Node auto-instrumentation can patch `http` before it's required. `app.onError` in `app.ts` calls `Sentry.captureException(err)` alongside the existing `console.error(err)`, only for the genuinely-unexpected (`INTERNAL_ERROR`) branch — not for `AppError`/`HTTPException`, which are expected/handled errors. Deliberately not using `@sentry/hono/node`'s `sentry(app)` request-tracing middleware — plain `Sentry.init()` already gives request context via Node's auto http instrumentation, and adding the middleware on top would need verifying its interaction with our own centralized `onError` (ordering/double-capture) before trusting it; skipped for now since capturing errors, not full APM tracing, was the actual ask. Not yet verified against a real Sentry project (no DSN configured) — typecheck-verified only.
- Seat-based Stripe billing: `BillingGateway` interface + `plans`/`BillingEvent` types (`packages/core/src/billing/types.ts`), `StripeBillingService` adapter (`apps/api/src/modules/billing/stripe-billing.service.ts` — the only file allowed to import `stripe`), a `billing` table FK'd to `organization.id` (`packages/db/src/schema.ts`, migrated onto the real Neon DB), `POST /billing/checkout` (gated by `requirePermission({ billing: ["manage"] })` + `requireOrgContext`, owner/admin only, request body validated via `@hono/zod-validator`'s `zValidator` middleware) and `POST /billing/webhook` (both routes down to a single call each — `billing.handlers.ts`'s `processWebhook` does the signature-verify/parse/dispatch sequence for the webhook route, per AGENTS.md's "route handlers are delivery-layer glue" rule) in `apps/api/src/modules/billing/billing.routes.ts`, and `enforceSeatLimit` middleware (`apps/api/src/middleware/seat-limit.middleware.ts`). Fully live-verified now: `STRIPE_SECRET_KEY` (a restricted key, not a full secret key — see `stripe-best-practices` skill), `STRIPE_WEBHOOK_SECRET` (from `stripe listen`), and `STRIPE_PRICE_STARTER`/`STRIPE_PRICE_GROWTH` (real test-mode Products/Prices, one Product per tier) are all configured. `POST /billing/checkout` confirmed returning a real `checkout.stripe.com` URL from the live Stripe API for an owner on the `starter` plan. A permanent test, `apps/api/src/modules/billing/billing.integration.test.ts`, covers: unauthenticated → 401, member without `billing:manage` → 403, a plan with no price (`free`) → 422, an owner on a billable plan → real Stripe checkout URL (`it.skipIf` when no price is configured, so the suite still runs without Stripe set up), and the webhook route: missing/invalid signature → 422, an unmapped event type → 200 with no DB write, and a signed `checkout.session.completed` (HMAC-signed with the real `STRIPE_WEBHOOK_SECRET`, not a live Stripe call) → 200 and a correctly-updated `billing` row. 17/17 tests pass (includes a dedicated case confirming a malformed body gets rejected in this app's own `{ success, error }` envelope, not `@hono/zod-validator`'s default response shape); DB confirmed self-cleaning (zero leftover rows after a run). **One thing that genuinely can't be automated**: completing the actual Stripe Checkout page (entering the test card `4242...`) is a hosted, browser-only flow with no server-side "complete this payment" API — so a real human paying through the full UI has only been reasoned about, never exercised end-to-end by anything running here. `enforceSeatLimit` also isn't attached to any route yet — there's no "add org member" endpoint of our own to attach it to (Better Auth's own `addMember`/invitation-acceptance handlers aren't routes we control); it's ready but genuinely unwired, same as the `student-progress` stub below.
- Two permanent automated tests now exist in `apps/api` (previously all verification was manual/throwaway): `src/lib/response.test.ts` (pure unit, `hono/testing`'s `testClient`, no DB) and `src/modules/notifications/websocket.integration.test.ts` (integration — real server, real `ws` client, real DB, self-cleaning). `apps/api/vitest.config.ts` + `vitest.setup.ts` added to make `process.loadEnvFile()` load `.env.development` for tests, since Vitest's CLI has no `--env-file` support.

## Bugs found and fixed along the way (worth knowing so they aren't reintroduced)

- Passing a custom `roles` map to Better Auth's `organization` plugin **replaces** its defaults rather than merging — since only `member`/`admin` were defined, every org's auto-assigned `owner` (its creator) had _zero_ permissions until `ownerRole` was added explicitly.
- `betterAuth()` had no `trustedOrigins`, so it rejected requests from origins the Hono CORS middleware was already allowing — two separate checks. `trustedOrigins` now reads the same `ALLOWED_ORIGINS` env var as the CORS middleware, so they can't drift apart.
- `NODE_ENV=<mode>` lines inside `.env.*` files were dead weight once `cross-env` was introduced (`cross-env` sets it before `--env-file` would even load, and `--env-file` never overrides an already-set var) — removed, including deleting the then-empty `.env.production`.

## Removed — deliberately deferred, not lost

`packages/core/src/algorithms/` (BKT scoring stub) and `packages/core/src/ai/*` (agent types, Claude client, an `exercise-generator` agent, registry) were built early, then deleted. Decision: the SaaS foundation (auth, permissions, response contract) should be product-agnostic and reusable first; product-specific logic (AI agents, education-specific algorithms) comes later, designed against real requirements instead of speculatively. Also removed: the `@anthropic-ai/sdk` dependency from `packages/core/package.json` (nothing used it anymore) and the `"./ai"` export from that package's `exports` map. `packages/core/src/index.ts` no longer re-exports either. Confirmed via `pnpm install` + typecheck across all packages after removal — nothing else referenced them.

If/when this comes back: don't recreate the old structure from memory — redesign it against whatever the actual product requirement is at that point. The old `AIAgent<TInput, TOutput>` contract + registry pattern is a reasonable starting reference but isn't gospel.

## Not done

- Invitation flow (`createInvitation`/`acceptInvitation`) not tested — the permission test added members server-side via `addMember` instead. The invite email/token round-trip itself hasn't been exercised.
- **No isolated test database.** `.env.test`'s `DATABASE_URL` points at a local Postgres placeholder (`localhost:5432`) that isn't actually running/wired to anything. Integration tests (e.g. `websocket.integration.test.ts`) currently run against the real dev Neon database instead, relying on strict self-cleanup (`afterAll` deletes what the test created) rather than isolation. Fine for now with one integration test; will need a real fix (a dedicated test DB + migration step in CI, or similar) before there are enough integration tests for collisions/flakiness to become likely.
