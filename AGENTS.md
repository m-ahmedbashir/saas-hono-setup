# AGENTS.md

Instructions for any AI coding agent working in this repository. Read before touching code. If this conflicts with what you observe in the repo, the repo wins — update this file, don't silently ignore it.

Standing rules — apply to every future file. For what's actually built and verified right now, see [PROGRESS.md](./PROGRESS.md); don't assume something exists just because a rule here describes how it _should_ behave.

## What this is

`saas-hono-setup` — pnpm + Turborepo monorepo. Hono API (`apps/api`) + Postgres/Drizzle (`packages/db`) + environment-agnostic domain logic (`packages/core`, testable without a server). Current focus: a generic multi-tenant SaaS foundation (auth, permissions, response contract, billing) reusable regardless of product. Product-specific logic (AI agents, algorithms) is deliberately deferred — see PROGRESS.md.

[ARCHITECTURE.md](./ARCHITECTURE.md) is the bird's-eye view — how the apps/packages fit together and how the main flows (requests, sign-in, checkout, notifications) move through them. This file governs _how to work here_. PROGRESS.md tracks _what's done_. (`architecture-and-agents.md` is the original MindLeague-era blueprint, kept for history only — much of what it describes was later removed.)

## Ground rule: don't scaffold ahead of the task

This repo was previously over-scaffolded in one sitting (algorithms + AI agents built before auth even booted). Don't repeat that:

- Build the feature asked for and the minimum it needs to run — not its neighbors "while we're in there."
- Check PROGRESS.md's "scaffolded but not wired" list before adding a new module — extend or delete an existing stub, don't leave a second parallel one.
- Verify what you built actually runs (boot the server, hit the endpoint, run the test) before moving on — typecheck alone doesn't catch a route that compiles but is never invoked.

## Architecture: DDD layering + SOLID

- **Domain** (`packages/core`) — pure business logic. No Hono, no HTTP, no network calls.
- **Infrastructure** (`packages/db`, `packages/core/src/auth`) — Drizzle schema/queries, Postgres connection, Better Auth construction.
- **Application** (`apps/api`) — delivery layer only: receive request, validate, call Domain/Infrastructure, shape response. No business logic in a route handler.

SOLID at the file level, as you write, not as a retrofit:

- **SRP** — a route file routes, a `.db.ts` file queries. Two reasons-to-change means split the file.
- **OCP** — a new feature slice is a new file, not an edit to an unrelated one (a registry/barrel needing a one-line addition to register it is the accepted exception).
- **LSP** — don't bake single-implementation assumptions (one DB driver, one vendor) into code meant to work for any implementation of a contract.
- **ISP** — routes expose precise, per-route Zod schemas/RPC types, never one monolithic type forcing a client to depend on unused fields.
- **DIP** — high-level code depends on an interface, not a low-level tool's concrete API directly. Accepted exception: `packages/core/src/auth/index.ts` imports `db` from `@repo/db` for Better Auth's `drizzleAdapter()` — that library's adapter API has no abstraction to invert against. Don't copy this pattern elsewhere without the same justification. A vendor-coupling gap (e.g. hard-coding one AI provider's SDK) is fine to leave alone _only_ while nothing calls it yet — fix it when the first real caller shows up, not before.

## Structure

```
apps/api/                  Hono server (deployable)
  src/app.ts                 builds/exports the Hono `app` + AppType — no serve()/side effects, importable from tests
  src/index.ts               process entrypoint only: serve(app) + injectWebSocket(server)
  src/middleware/            cross-cutting Hono middleware
  src/lib/                   HTTP-layer helpers (e.g. response envelope) — not domain logic
  src/modules/<feature>/    one folder per feature slice: *.routes.ts, *.controller.ts, *.db.ts, *.schema.ts, *.service.ts/*.handlers.ts as needed

packages/db/                Drizzle schema + client, owns migrations
  src/schema.ts              table definitions — single source of truth for DB types
  src/index.ts               `db` client export + re-exported drizzle-orm operators
  drizzle.config.ts

packages/core/              environment-agnostic logic — no Hono/HTTP/socket imports
  src/auth/                  Better Auth config + access control
  src/errors.ts              AppError + error codes
  src/notifications/types.ts NotificationDispatcher interface — contract only
  src/billing/types.ts       BillingGateway interface — contract only
```

Interface/adapter split: the _interface_ lives in `packages/core` (pure contract — e.g. `NotificationDispatcher<TClient>`, generic so core never knows what a "client" concretely is); the _implementation_ that touches a real transport/vendor object lives in `apps/api` (e.g. `websocket-dispatcher.ts`, `stripe-billing.service.ts`). Follow this for any future interface/adapter pair.

Product-specific domain modules (algorithms, AI strategies) aren't scaffolded yet — when built, a new subfolder under `packages/core/src/`, same "pure logic" rule as everything else there. Don't invent the layout before there's a real module.

Rules from this layout:

- `packages/core` never imports from `apps/api` or Hono — must stay usable from a script, a test, or a future non-HTTP entrypoint.
- `packages/db` is the only place table shapes are defined. Derive types (`typeof table.$inferSelect`), never hand-write a duplicate interface.
- Import Drizzle operators (`eq`, `count`, etc.) from `@repo/db`'s re-export, not `drizzle-orm` directly in `apps/api` — a direct dependency there can resolve a _different_ pnpm-isolated `drizzle-orm` instance (e.g. once another dependency pulls in `@opentelemetry/api`, an optional peer) with incompatible types despite matching versions. Add missing operators to `@repo/db`'s re-export instead.
- **Detect a Postgres error with `isUniqueViolation(err, constraint?)` from `@repo/db`, never by reading `err.code` directly.** Since drizzle-orm 0.44 every failed query throws a `DrizzleQueryError` with the driver's error on `.cause`, so a bare `err.code === "23505"` check never matches. That silently broke duplicate-plan detection (500 instead of 422) and `ensureOrganizationProfileRow`'s race fallback until the 0.45 upgrade's tests caught it. Add any other SQLSTATE helper next to it in `packages/db/src/pg-errors.ts`.
- A feature slice gets `.routes.ts` (router), `.controller.ts` (named HTTP handler functions), `.db.ts` (queries), `.schema.ts` (Zod). Don't put query logic in a route handler.
- **No handler function body ever lives in `.routes.ts` — hard rule, no "it's just one call" exception.** `.routes.ts` is a manifest: for each route, the path, its middleware/validators (inline is fine — see below), and a **named reference** to a handler function, never a function literal. The handler itself — even a trivial one-call-and-respond handler — lives in `<feature>.controller.ts`, one exported function per route. Multi-step business logic (a `switch` deciding what an input means, several calls in order) still doesn't belong in the controller function either — pull that into `<feature>.service.ts` (called directly) or `<feature>.handlers.ts` (reacting to an event/webhook, e.g. `billing.handlers.ts`'s webhook processing); the controller function calls it and shapes the response. Reference: `apps/api/src/modules/billing/` (`billing.routes.ts` + `billing.controller.ts` + `stripe-billing.service.ts` + `billing.handlers.ts`).
  - **Separate controller files keep end-to-end type inference — verified, not assumed** (specs/typed-api-client-plan.md Task 1). Hono's docs warn that "Rails-like controllers" lose inference; that's about the _input_ side when a handler is written without its validator. Here the validators stay inline in the `.routes.ts` chain (request types come from them) and response types come from the controller's inferred `success(c, data)` return, so `hc<AppType>` sees both. `apps/api/src/client-types.test.ts` proves it with `expectTypeOf` against the services' own types. Two things would break it: **annotating a controller's return type** (e.g. `Promise<Response>` erases the typed response — let it infer), and **declaring a service result narrower than what it returns** (notifications' list was annotated as core's `NotificationRecord`, which hid the `read` flag every row carries; derive from the query instead).
  - Middleware/validators stay inline in `.routes.ts` (`injectUserContext`, `requirePermission(...)`, a `zValidator` bound to one route's schema) — only the terminal handler moves out. Extract middleware to a named file in `apps/api/src/middleware/` only when it's reused across routes.
  - **A controller handler that reads `c.req.valid(target)` needs an explicit `Context` type reconstructing `@hono/zod-validator`'s output shape** (`Context<any, string, { in: { json: z.input<Schema> }; out: { json: z.output<Schema> } }>`) — pulling the handler out of the same `.post(path, validator, handler)` chain it's validated in loses TypeScript's contextual inference for `.valid()`; a plain `Context` types it as unusable (`never`). `billing.controller.ts`'s `ValidatedJsonContext<Schema>` is the reference pattern — reuse it, don't re-derive it per feature.
  - One exception to "one call" inside a controller function: narrowing a discriminated union (e.g. `UserContext`'s `B2C | B2B2C`) doesn't survive a middleware→handler boundary in Hono's type system, so a handler needing `organizationId` legitimately needs one narrowing call (`requireOrgContext`, `apps/api/src/middleware/auth.middleware.ts`) before its one real call. That's narrowing glue, not business logic.
  - **`app.ts` follows the same rule** — it's not a feature slice, so its root-level hooks (`.get("/health", ...)`, `app.notFound(...)`, `app.onError(...)`) are named functions in `apps/api/src/lib/app-handlers.ts`, not inline, same as any other handler. `onError` especially: it branches on error type (`AppError` / `HTTPException` / unknown), which is exactly the "multi-step logic doesn't live where it's registered" case this rule exists for.

## Type safety (non-negotiable)

- Never hand-write a type duplicating a Drizzle table or Zod schema — derive it (`typeof x.$inferSelect`, `z.infer<typeof Schema>`).
- Prefer `satisfies` over a type annotation for config/strategy objects — keeps literal types intact.
- Check `@repo/db`/`@repo/core` for an existing shape before declaring a new type.
- **Frontends get `apps/api` types from `AppType` and Better Auth types from Better Auth — never hand-write either.** Each app's `src/lib/api.ts` is `createApiClient<AppType>(NEXT_PUBLIC_API_URL)` (`@repo/shared/hc-client`, Hono's `hc` client), and every call is `unwrap(await api.<route>.$get(...))` (`@repo/shared/api-response`, which throws `ApiError` on a failure envelope). A component that needs a name for a shape derives it from the service (`Awaited<ReturnType<typeof getX>>`, `InferRequestType<...>["json"]` for payloads); Better Auth shapes come from its own exported types (e.g. `UserWithRole` from `better-auth/plugins/admin`) or hooks (`apps/portal/src/features/team/types.ts`). Only UI-only state (filters, form values) is hand-written. Reference: `apps/admin/src/features/subscription-plans/api/service.ts`.
  - **`AppType` is a type-only import** (`import type { AppType } from "@repo/api/client-types"`) — enforced by a `no-restricted-imports` lint rule in both apps; `@repo/api` is a devDependency, so no server code can reach a browser bundle.
  - **Dates arrive as strings.** `hc` types a JSON response as JSON (`Date` → `string`), which is what the wire carries — wrap in `new Date(...)` to format. (Better Auth's own client is different: it parses ISO dates, so its `Date` fields really are `Date`s.)
  - **Don't derive a Better Auth type via `ReturnType<typeof authClient.x.y>`** — those methods are generic over their fetch options, and `ReturnType` of them collapses to `any`. Use Better Auth's exported type instead. Every derived type has a `@ts-expect-error` guard on a non-existent field (e.g. `apps/admin/src/features/staff/api/service.test.ts`) so a collapse to `any` fails `typecheck` instead of passing silently.
  - **`hono` is pinned to the same exact version in `apps/api`, `apps/portal`, `apps/admin` and `packages/shared`** — mismatched copies break `hc`'s type inference. Bumping it means bumping all four together.

## Data shaping & request validation

- Never return a raw `db.select().from(table)` row — select only needed fields (avoids leaking columns like password hashes and reduces payload size).
- Every route with a body/query validates via `@hono/zod-validator`'s `zValidator(target, schema, hook)` as route middleware — a real pre-route guard, not `.safeParse()` inside the handler. Handler reads `c.req.valid(...)`, never `c.req.json()` directly. The `hook` is required: without it, a failure returns the library's own shape, not this app's `{ success, error }` envelope — the hook must re-throw `AppError("VALIDATION_ERROR", message, details)`. For Zod v4, build `details` with `flattenError(result.error)` from `"zod"` — the hook's `result.error` is zod's core `$ZodError`, which has no `.flatten()` method the way a plain `.safeParse()` result's classic `ZodError` does. Reference: `billing.routes.ts`'s `validateCheckoutBody`.

## Auth model

Better Auth + Organization plugin is the single identity system for B2C (individual), B2B (org), B2B2C (org-sponsored individual). `packages/core/src/auth/index.ts` is the only place `betterAuth(...)` is constructed.

- Protect a route with `injectUserContext` (`middleware/auth.middleware.ts`), read `c.get('userContext')` — branch on its `mode: 'B2C' | 'B2B2C'` discriminant, don't assume an org exists.
- Gate by permission with `requirePermission(permissions)` (`middleware/permission.middleware.ts`), after `injectUserContext`. Checks B2B2C members via the same `Role` objects Better Auth's own plugin uses internally (`roles`, `packages/core/src/auth/permissions.ts`) — not `auth.api.hasPermission(...)`, which would re-derive the session and re-fetch the member's role from the DB, both already resolved moments earlier by `injectUserContext` in the same request. See "Production hardening" for why this is safe. B2C passes through by design (an individual's access to their own data is an ownership check in `.db.ts`, not a permission lookup).
- Permissions/roles live in `packages/core/src/auth/permissions.ts` via `createAccessControl`. `statement` is the source of truth; `ownerRole`/`adminRole`/`memberRole` are named bundles of it; `roles` (`{ owner, member, admin }`) is the single shared map both the `organization` plugin config and `requirePermission` use.
- **A custom `roles` map on the `organization` plugin replaces Better Auth's defaults, doesn't merge.** Every role needing plugin permissions — including auto-assigned `owner` — must be defined explicitly or it silently gets zero permissions.
- `betterAuth()`'s `trustedOrigins` must read the same `ALLOWED_ORIGINS` as the Hono CORS middleware — two separate checks, don't let them drift.
- CORS doesn't cover WebSocket handshakes (only `fetch`) — a WS route needs its own explicit `Origin` check against `lib/allowed-origins.ts` (see `notifications.routes.ts`). Don't rely on the session cookie's `SameSite` default to prevent cross-site WS hijacking — that's a client-side behavior this repo may need to relax once frontend/API are on separate domains.
- Auth routes (`modules/auth/auth.routes.ts`) are unauthenticated by definition, just proxy to `auth.handler` — don't add `injectUserContext` there.
- **Rate limiting is Better Auth's own** (`packages/core/src/auth/rate-limit.ts`), on in production only:
  - `storage: "database"`, never memory: memory counts per API instance, so the real limit would multiply by the instance count. It needs better-auth >= 1.7.7's atomic `consume()`.
  - The key is the client IP from `cf-connecting-ip` alone, which is safe only because the origin accepts Cloudflare traffic only (README's Deployment notes). Never add `x-forwarded-for` or another header a client can set. A request with no trusted IP falls into one shared `no-trusted-ip` bucket (verified in 1.7.12's `rate-limiter/index.mjs`), so a missing header throttles collectively rather than not at all.
  - `rate-limit.integration.test.ts` builds extra instances via `createAuth({ rateLimitEnabled: true })` to prove the 429, per-client isolation, and the limit holding across two instances. Production code only ever uses `auth`.
  - `rate_limit` is generated, but its `last_request` index is ours (migration 0022). Better Auth's cleanup `deleteMany(lastRequest < cutoff)` runs on every window reset, and a plain Node server awaits it inside the request. **Keep the index when merging a regenerated schema.**

### Auth-related tables are generated, never hand-edited

`user`, `session`, `account`, `verification`, `organization`, `member`, `invitation` in `packages/db/src/schema.ts` came from Better Auth's CLI, not hand-written. When a plugin is added/removed/reconfigured, regenerate — don't guess the new shape:

```
npx auth@1.7.12 generate --config packages/core/src/auth/index.ts --output packages/db/src/auth-schema.generated.ts
```

Diff against `schema.ts`, merge changes, delete the temp file, run `pnpm db:generate && pnpm db:migrate`. Non-auth tables (e.g. `billing`) don't go through this.

## Billing model

`BillingGateway` (`packages/core/src/billing/types.ts`) — vendor-agnostic contract (`createCheckoutSession`, `createIndividualCheckoutSession`, `updateSubscriptionQuantity`, `cancelSubscription`, `parseWebhookEvent`, `validatePriceId`). `StripeBillingService` (`apps/api/src/modules/billing/stripe-billing.service.ts`) is the concrete adapter.

- **No file outside `stripe-billing.service.ts` may import `stripe`** — including its types. The webhook route only ever sees the normalized `BillingEvent` union from `parseWebhookEvent`, never Stripe's raw event shape — this is what makes swapping vendors a one-file change.
- **Plans are admin-editable rows, not hardcoded maps.** `packages/db`'s `subscriptionPlans` table (see specs/subscription-management-plan.md) replaced the old `organizationPlans`/`individualPlans` maps — `OrganizationPlanId`/`IndividualPlanId` are now plain `string` aliases, not closed unions. `apps/api/src/modules/subscription-plans/` owns the catalog: CRUD gated by `requirePlatformPermission({ subscriptionPlans: [...] })` (`list` for admin+support, `manage` for admin-only), no hard delete (`isActive: false` retires a plan instead). Global config, not RLS-scoped — see the Row-Level Security section below for why.
- **`BillingGateway`'s checkout methods take an already-resolved `providerPriceId`, not a `planId` to look up internally.** `apps/api/src/modules/billing/billing.service.ts` (not `stripe-billing.service.ts`) resolves a `planId` to a real Stripe price via `subscription-plans.service.ts`'s `getPlanForBilling` before ever calling the gateway — keeping the vendor adapter with zero dependency on the plan catalog, which is also what keeps the billing and subscription-plans modules from circularly depending on each other (subscription-plans.service.ts calls `stripe-billing.service.ts`'s `validatePriceId` for admin-plan-creation checks; nothing in `stripe-billing.service.ts` calls back into subscription-plans).
- **Organization and individual billing are two separate tables and two separate flows — not one polymorphic model.** `organization_billing` (FK'd to `organization.id`) is seat-based. `individual_billing` (FK'd to `user.id`) has no seat/quantity concept at all. Neither is columns added to its generated/owning table (`organization`/`user` are both Better-Auth-generated and would drift on regeneration) — same "own table" reasoning as the auth tables section below. Reference files: `organization-billing.db.ts` / `individual-billing.db.ts`, `billing.routes.ts`'s two checkout routes.
- **A billing row's `plan` string alone can't tell you which `subscription_plans` row it means** — resolving it needs the owning `organizationId` too, since an org can have its own custom plan reusing the same slug as a shared one. `subscription-plans.db.ts`'s `getSubscriptionPlanForBilling` checks a custom (org-scoped) match first, then falls back to the shared (`organizationId IS NULL`) one; individual lookups always pass `organizationId: null` and skip straight to shared.
- `POST /billing/organization-checkout` requires `requirePermission({ billing: ["manage"] })` + `requireOrgContext` — owner/admin only, for the org's active org. `POST /billing/individual-checkout` requires only `injectUserContext`, scoped to `userContext.user.id` — an ownership check, not a permission one (same reasoning as B2C data access elsewhere: there's no org role to check against). Works identically for a B2C or B2B2C session, since every session has a user.
- **Customers see the plan catalog through `GET /billing/organization-plans` / `GET /billing/individual-plans`, never `/subscription-plans`** (platform-staff-only). Read-only, viewable by any active-org member (only _buying_ is `billing:manage`-gated), and a projection, not the raw row: `providerPriceId` is replaced by `isPurchasable`, and the org list applies the same custom-then-shared precedence as `getSubscriptionPlanForBilling` (an org's custom plan hides a shared plan with the same slug) — otherwise the list would offer a plan checkout would never resolve to for that org. The individual list never includes any org's custom plans.
- **"Is a subscription live?" has one definition — `isLiveSubscription` (`packages/core/src/billing/subscription-status.ts`)**: any status but `canceled`/`null`. Checkout, cancel, and `apps/portal`'s UI all use it (the portal via the side-effect-free `@repo/core/billing/subscription-status` subpath). Don't re-derive it from `providerSubscriptionId` — that id deliberately stays on the row after the subscription ends.
- **Checkout refuses while a subscription is live** (422) — checkout always creates a _new_ Stripe subscription, so a second one would double-bill and its webhook would overwrite `providerSubscriptionId`, orphaning the first from cancel. Switching plans = cancel first. **Organization checkout also enforces seats server-side**: at least the current member count, at most the plan's `seatLimit`. Cancel refuses when nothing is live, rather than calling Stripe on an ended subscription.
- **When a subscription ends, the webhook resets `plan` to the owner type's default plan** (`customer.subscription.deleted`, or `.updated` with a canceled status — `billing.handlers.ts`'s `endsSubscription`). `plan` is what `requireFeature` and the seat limit (`getOrganizationSeatUsage`) resolve from, so leaving the paid plan on a canceled row would keep granting it. The webhook stays the single writer; readers never re-derive "is this still paid for". `providerSubscriptionId` is kept so late events for the ended subscription still resolve to their owner. Migration `0020_reset_ended_subscription_plans.sql` backfilled rows canceled before this rule existed.
- **Custom-vs-shared plan precedence lives in exactly one function — `applyCustomPlanPrecedence` (`subscription-plans.db.ts`)** — used by both `getSubscriptionPlanForBilling` (entitlements, seat limit, checkout) and the customer plan list. An org's custom plan shadows the shared one with the same slug **even when the custom one is inactive** (its existing subscribers keep their entitlements; the shared plan isn't offered since checkout would resolve to the retired deal). Apply precedence first, filter by `isActive` second.
- `BILLING_CHECKOUT_RETURN_URL` points at `apps/portal`'s `/billing` (customers check out from the portal; `apps/admin` has no billing page). Stripe returns with `?checkout=success|cancelled`, which the page acknowledges — the plan itself changes only once the webhook lands.
- `POST /billing/webhook` is unauthenticated (Stripe calls it directly), verified by signature via `parseWebhookEvent` instead, and its response isn't wrapped in the envelope (Stripe only checks HTTP status). `BillingEvent`'s `checkout_completed` variant is a discriminated union on `ownerType: "organization" | "individual"` — `billing.handlers.ts` branches on it to decide which table to write to. `subscription_updated`/`subscription_canceled` events don't carry an owner id at all (only a Stripe subscription id), so the handler updates _both_ tables unconditionally by `providerSubscriptionId` — safe because Stripe subscription ids are unique per subscription and each checkout writes to exactly one table, so the non-matching table's update is always a harmless no-op. Don't "optimize" this into a single lookup-then-update without re-verifying that reasoning.
- **Seat limits are enforced by Better Auth's own `membershipLimit` hook**, not a route middleware — it's checked on every accepted invitation and every server-side `addMember` (verified in the installed `crud-invites.mjs`/`crud-members.mjs`), so no path to joining an org skips it; a refusal is Better Auth's `ORGANIZATION_MEMBERSHIP_LIMIT_REACHED` (403). The limit itself is `billing.service.ts`'s `getOrganizationSeatLimit` (the plan's `seatLimit` via the same custom-then-shared lookup; `null` = no cap; an unresolvable plan fails closed). Because `packages/core` can't import `apps/api`, core defines the contract (`packages/core/src/auth/membership-limit.ts`) and `apps/api/src/lib/auth-wiring.ts` registers the implementation, imported by `app.ts`. An unregistered resolver throws — every join refused — rather than silently using Better Auth's default of 100. (This replaced an earlier `enforceSeatLimit` middleware that was never attached to any route.) Individual billing has no seat concept.

## Feature Entitlements

In-house, zero-dependency plan-based feature gating — see `ENTITLEMENTS.md` for the full design rationale (why not a third-party service, why each deviation from the obvious naive design). Compressed rules:

- `packages/core/src/billing/entitlements.ts` — `PlanEntitlements` (boolean `features` + numeric `limits`), `FeatureKey`/`PlanLimitKey` (the one closed vocabulary that never moves to the database — see the Billing model section above), and `featureKeys`/`limitKeys` runtime companions derived from a `Record<Key, true>` registry (an omitted key is a `tsc` error). `resolvePlanEntitlements(raw)` re-validates a plan row's JSONB against those keys on every _read_, not just at the write boundary — unknown keys dropped, missing known keys default to `false`/`0`. `fallbackEntitlements` is a small deny-most constant for when a plan row genuinely doesn't exist (never for a merely-deactivated plan, never for a DB error). `canAccessFeature(entitlements, feature)`/`getPlanLimit(entitlements, limit)` are pure — no DB/HTTP, take an already-resolved `PlanEntitlements` directly (no more `BillingOwner`; resolving _which_ plan row applies is `apps/api`'s job now, via `subscription-plans.service.ts`).
- `apps/api/src/middleware/entitlement.middleware.ts` — one middleware, `requireFeature(feature, scope)`, for the whole app (both billing universes), after `injectUserContext`. **`scope: "organization" | "individual"` is a required argument, never inferred from `userContext.mode`** — a B2B2C session having an active org doesn't mean every route it hits is an org-level feature; inferring scope from session state would silently check the wrong plan's entitlements for a personal-feature route. The route author declares which billing entity gates it.
- Denial throws the existing `PAYMENT_REQUIRED` code — don't add a new `ErrorCode` for this. `scope: "organization"` with no active org throws `requireOrgContext`'s `VALIDATION_ERROR` instead — a different problem ("no org") than "plan too low," kept as a different code on purpose.
- Resolves the current plan via the same RLS-respecting helpers as everything else touching billing tables (`withOrgScope`/`getBillingByOrgId`, `withUserScope`/`getUserBillingByUserId`) — never the bare `db` client — then, if no billing row exists yet, falls back to `subscription-plans.service.ts`'s `getDefaultPlanId(ownerType)` (the current `isDefault: true` shared plan), not a hardcoded `"free"`/`"individual_free"` string. The resulting `planId` goes through `resolveEntitlementsForPlan` before `canAccessFeature` ever sees it.
- No route in this repo uses `requireFeature` yet — don't invent a placeholder feature module (`ai.routes.ts`, `student-progress.routes.ts`) just to wire it in; that's exactly the ahead-of-task scaffolding this repo's ground rule warns against. `entitlement.integration.test.ts` proves the middleware against a test-only route on a standalone `Hono` instance instead.

## User Profile

`profile` (`packages/db/src/schema.ts`) — phone, `dateOfBirth`, structured address (`addressStreet`/`addressCity`/`addressState`/`addressPostalCode`/`addressCountry`). One row per user, FK'd to `user.id`, lazily created on first `PATCH` (not at signup) — same "own table, not columns on the generated table" reasoning as `organizationBilling`/`individualBilling`, and the same ownership model as individual billing: works identically for B2C and B2B2C, no org concept at all.

- **`dateOfBirth`, not a raw `age`** — an age goes stale the moment a year passes; `dateOfBirth` is the actual source of truth, `profile.schema.ts` also bounds it (not in the future, not >130 years ago).
- **Address is structured, not one free-text column** — usable for shipping/tax/filtering later. `addressCountry` is validated as an ISO 3166-1 alpha-2 code, not a free-text country name, at the app boundary (`packages/db` can't import Zod).
- `GET`/`PATCH /profile` — `injectUserContext` only, no `requirePermission`/`requireOrgContext`, same reasoning as `/billing/individual-checkout`.
- `PATCH`'s Zod schema makes every field `.optional()`, distinct from `.nullable()`: an **omitted** field means "leave unchanged," an explicit **`null`** means "clear it" — `profile.service.ts`'s `updateProfile` only spreads a DB column into the update payload when the corresponding input field is `!== undefined`. Don't collapse that distinction (e.g. by defaulting missing fields to `null`) without checking every caller still means what it says.
- RLS-enabled (`withUserScope`, same as `individual_billing`) — profile data is at least as sensitive as billing plan info.

## Organization Profile

`organization_profile` (`packages/db/src/schema.ts`) — `orgNumber`, industry, `companySize`, website, phone, `taxId`, description, structured address (same shape as `profile`'s). One row per org, FK'd to `organization.id`.

- **`orgNumber` is a permanent, human-friendly, unique, indexed identifier** — 8 characters, cryptographically random (`randomInt`, not `Math.random`), drawn from an alphabet with ambiguous characters removed (`0`/`O`, `1`/`I`/`L`) so it's safe to read aloud or transcribe by hand. Generated and collision-retried in `packages/db/src/organization-profile.ts`'s `ensureOrganizationProfileRow` — not in `packages/core`, where a pure generator like this would normally belong, because `packages/core` already depends on `@repo/db` (for the Better Auth adapter), so the reverse import would be a circular workspace dependency. Same constraint already documented on `organizationBilling`'s `plan` column.
- **Deliberately NOT intended to double as a future join/invite credential.** If a "let a user enter this to join an org" feature gets built later, it should use a separate, rotatable, rate-limited secret — not this field. A permanent 8-character code with no rotation or rate-limiting would become a standing "master key" to self-join any org if used directly as a join credential. `orgNumber` stays a low-sensitivity identifier (fine to display, log, or reference in support), not an authorization boundary.
- **Created eagerly, at org creation — not lazily on first access, unlike every other table in this file.** Wired via Better Auth's real `organizationHooks.afterCreateOrganization` hook (`packages/core/src/auth/index.ts`) — verified to exist in the installed version before relying on it, not assumed. This is a second instance of this file's one documented DIP exception (`packages/core/src/auth/index.ts` importing `db` for the adapter) — Better Auth's hook API can only be wired inside that same `betterAuth()` config, so any code that must run there is forced to be reachable from `packages/core`, whether that's the "natural" layer for it or not. `getOrganizationProfile`/`updateOrganizationProfile` (`apps/api`) also call the same `ensureOrganizationProfileRow` defensively on every access — idempotent, so this is cheap, and it backfills orgs created before this feature existed or any other edge case where the hook didn't run.
- **`ensureOrganizationProfileRow`'s retry-on-collision runs each insert attempt inside a `tx.transaction(...)` savepoint, not directly on the passed-in `tx`.** Postgres aborts an entire transaction after any failed statement until it's rolled back — retrying more statements straight on `tx` after a unique violation would just fail again with "current transaction is aborted." Confirmed against drizzle-orm's actual node-postgres driver source (`NodePgTransaction.transaction` issues a real `SAVEPOINT`/`ROLLBACK TO SAVEPOINT`), not assumed to work. After a violation, it re-checks for the row by `organizationId` before regenerating — distinguishes "the orgNumber collided" (rare, regenerate and retry) from "a concurrent caller already created this org's row" (return that row, don't error).
- `GET /organization-profile` — any member of the active org (`injectUserContext`, handler narrows via `requireOrgContext`), no extra permission — viewing shared org reference info isn't a role-gated action. `PATCH /organization-profile` — owner/admin only, via a dedicated `organizationProfile: ["manage"]` permission (`packages/core/src/auth/permissions.ts`), not `billing`'s — gating profile edits on an unrelated permission would violate ISP.
- `orgNumber` is never accepted in the `PATCH` body — it's not in `updateOrganizationProfileSchema` at all, so Zod strips a client attempt to set it silently; the response still reflects the real, system-generated value.

## Account deletion

`DELETE /account` (`apps/api/src/modules/account/`) — permanently deletes the authenticated user's own account and everything that belongs to it. `injectUserContext` only, no `requirePermission`/`requireOrgContext`, same ownership reasoning as `/profile`.

- **Blocks if the user is the sole `"owner"` of an org that still has other members** — throws `VALIDATION_ERROR` (422) telling them to transfer ownership or remove other members first, rather than silently orphaning the org. If they're the sole owner _and_ the only member, that org has nothing to hand off — it's deleted along with the account instead of left permanently orphaned.
- **Cancels any live Stripe subscription first (best-effort)** — both the account's own `individual_billing` subscription and any solo-owned org's `organization_billing` subscription, via `billingService.cancelSubscription` (implemented earlier, this is its first real caller). Swallows a Stripe failure (API down, no `STRIPE_SECRET_KEY` configured) rather than blocking deletion on it — a stray still-active subscription is a billing-ops follow-up, not a reason to refuse someone's own data-deletion request.
- **Deleting `user`/`organization` and trusting `ON DELETE CASCADE` to clean up their RLS-protected children (`profile`, `individual_billing`, `organization_billing`, `organization_profile`) is safe — cascade actions are not subject to Row-Level Security at all, even with `FORCE ROW LEVEL SECURITY`, even completely unscoped.** An earlier version of this note claimed the opposite (that an unscoped cascade delete gets blocked by the fail-closed policy) — that was wrong, and shipped without being empirically checked. Confirmed directly against the real database before correcting this: created an org with an `organization_profile` row, deleted the parent `organization` row via the bare, fully unscoped `db` client, and the cascade succeeded. **The one thing that still genuinely needs to happen before deleting the parent row is reading each RLS-protected child's `providerSubscriptionId`** (via `withOrgScope`/`withUserScope`, same as any other read of an RLS table) — not to delete it, but because it's needed for the pre-delete Stripe cancellation call, and the row won't exist to read afterward.
- Don't reintroduce explicit pre-deletion of these child rows "to be safe" — it's redundant now that the actual Postgres behavior is confirmed, and reintroducing it without re-verifying would just resurrect the same unverified claim this note corrects.
- `account.db.ts` introduces `AnyExecutor` (`packages/db/src/index.ts`) — `typeof db | DbExecutor` — for the handful of functions here that query non-RLS tables (`member`, `organization`, `user`) where scoping doesn't matter either way. RLS-enabled tables should keep requiring the stricter `DbExecutor`, not `AnyExecutor`, so a caller can't accidentally query them unscoped.
- `deleteAccount`'s solo-owned-org deletion calls `organization.service.ts`'s `deleteOrganization` rather than duplicating it — same subscription-cancel + delete sequence a direct `DELETE /organization` does.

## Organization deletion

`DELETE /organization` (`apps/api/src/modules/organization/`) — permanently deletes the caller's active organization and everything that belongs to _it_: billing, profile, memberships, pending invitations. Owner-only, via a dedicated `organization: ["delete"]` permission (`packages/core/src/auth/permissions.ts`) — not granted to `admin`, since this is more severe than anything `organizationProfile: ["manage"]` covers.

- **Never touches any member's own account — this is the actual GDPR-relevant property, not an implementation detail.** GDPR's right to erasure belongs to each individual data subject; an organization isn't a data subject at all, only the people in it are. Deleting an org has no bearing on its members' own personal data (`user`, `profile`, `individual_billing`) — those stay exactly as they were, under each person's own control. Deleting the org only ends everyone's _membership_ (their `member` row cascades away, same as if they'd been individually removed) — never their account. Only a member's own request (`DELETE /account`) can erase their own data. Directly proven, not just reasoned about: `organization.integration.test.ts` deletes an org with a non-owner member present and asserts both the owner's and the member's `user` rows still exist afterward.
- **No "block if other members exist" guard, unlike `DELETE /account`'s org-deletion path.** That guard exists specifically because deleting your _own_ account shouldn't _silently_ take an org other people depend on down with it as a side effect. This endpoint is the opposite case: an explicit, deliberate "delete this organization" action by its owner — there's no silent side effect to guard against, so it's allowed regardless of member count. Real product precedent for this shape (deleting a whole workspace/org outright, no "remove everyone first" step) — e.g. deleting a Slack workspace or Notion workspace.
- Cancels any live Stripe subscription first (best-effort, same reasoning as `DELETE /account`'s).

## Platform admin

Better Auth's own `admin` plugin (`packages/core/src/auth/index.ts`), enabled with its default config — not a hand-rolled system. There is deliberately no UI or custom route for this yet (no support/ops team exists to use one); this is the backend groundwork so a future admin panel has something real to call.

- **A completely separate concept from the `organization` plugin's roles, not a conflicting one.** Platform admin lives on `user.role` (one flag on the account itself); org roles live on `member.role` (per-org-membership). Both can independently use the string `"admin"` with zero collision — different columns, different plugins, checked by different code paths. Don't reach for `requirePermission`/`packages/core/src/auth/permissions.ts`'s `roles` for anything platform-wide; that map is the `organization` plugin's, entirely unrelated.
- **Every `/api/auth/admin/**` route is Better Auth's own** (list/get/create/update users, set-role, ban/unban, impersonate/stop-impersonating, revoke-session(s), remove-user, set-password, has-permission) — proxied through the existing `authRoutes` catch-all with zero custom code. No custom `admin.routes.ts`/`admin.controller.ts` exists or is needed for these; a future admin UI calls them directly, same as it would call any other Better Auth endpoint.
- **Bootstrapping the first admin** — `ADMIN_USER_IDS` (comma-separated, `packages/core/src/auth/index.ts`, see `.env.example`) grants specific user ids blanket admin access regardless of `user.role`, verified directly against the installed plugin's `has-permission.mjs` (`input.userId && options.adminUserIds?.includes(input.userId)` short-circuits to `true` before any role check runs). Unset/empty is a no-op, not "everyone is one." Once at least one real admin exists, `POST /api/auth/admin/set-role` is the normal way to promote further accounts — `ADMIN_USER_IDS` only exists to solve the chicken-and-egg problem of the very first one. A direct server-side `auth.api.createUser({ body: { ..., role: "admin" } })` call (no `headers` passed) is also a trusted path — verified against `routes.mjs`: the requesting-user permission check only runs `if (session)`, and there's no session on a headerless direct call.
- **Banning immediately revokes the user's existing sessions**, not just future logins — verified against `routes.mjs`'s `banUser` handler, which calls `internalAdapter.deleteUserSessions(...)` synchronously as part of the same request. A banned user's next session-creation attempt (a fresh login) is separately blocked by a `session.create` `before` hook that also auto-lifts an expired ban (`banExpires` in the past) rather than requiring a manual unban.
- **Two platform roles, `admin` and `support`** — custom `roles`/`ac` passed to the plugin (`packages/core/src/auth/platform-permissions.ts`), since a genuine second tier now exists (employees who need read-only visibility, not full control). **Passing a custom `roles`/`ac` map REPLACES the plugin's own defaults server-side, it does not merge with them** — verified directly against the installed plugin's `access/statement.mjs`/`admin.mjs` before doing this, not assumed. `platformAdminRole` deliberately replicates Better Auth's own default `adminAc` exactly (`user`: create/list/set-role/ban/impersonate/delete/set-password/set-email/get/update; `session`: list/revoke/delete) so the existing bootstrapped admin account keeps identical capabilities — notably still without `impersonate-admins`, matching upstream's default (not a regression, upstream's default admin role never had it either). `platformSupportRole` is read-only (`user`: list/get only) — can look employees up but can't ban/remove/change-role/impersonate/reset-password. **The client (`adminClient()` in `apps/admin/src/lib/auth-client.ts`) merges a custom `roles` map on top of its defaults instead of replacing** — a real asymmetry vs. the server, verified against `client.mjs`; the client is still configured to match, purely so TypeScript infers the `"support"` role correctly. The actual enforcement is server-side regardless.
- `admin-plugin.integration.test.ts` (`apps/api/src/modules/auth/`) proves both tiers are actually wired, not just configured: a regular user gets 403 from `/api/auth/admin/list-users`; a `user.role: "admin"` account (created via the trusted server-side `createUser` path above, since `ADMIN_USER_IDS` is read once from `process.env` at module load and can't include a not-yet-generated test user's id) can list users, set another user's role, and remove a user; a `user.role: "support"` account can list/get users but gets 403 on set-role/ban/remove.
- **"Add an employee" is admin-created, not self-signup** — `apps/admin`'s `/dashboard/users` page (`src/features/users/`) calls `authClient.admin.createUser({ name, email, password, role })` directly; there's no invite-email flow, the admin is expected to share the generated credentials out of band. Matches the product framing directly: platform staff are added by an existing admin, not invited to sign themselves up. Role changes/ban/remove all happen from the same table's row actions, each a direct `authClient.admin.*` call — no bespoke `apps/api` route exists or is needed for any of this, same reasoning as the rest of this section.
- **`PlatformAccessGate` (`apps/admin/src/features/users/components/platform-access-gate.tsx`) restricts `/dashboard/users` to `admin`/`support` roles client-side, via `useSession()`.** This is a UX convenience only (don't flash the page/nav item at someone who'd just get 403s from every real action) — it is emphatically not the security boundary. That's Better Auth's own permission check on every `authClient.admin.*` call, enforced server-side regardless of whether this gate exists at all.
- **`pnpm --filter @repo/api seed:admin`** (`apps/api/scripts/seed-admin.ts`) — the operator-facing equivalent of the trusted `createUser` path above, for seeding a real, loggable-in admin account instead of an id-based `ADMIN_USER_IDS` override. Reads `SEED_ADMIN_EMAIL`/`SEED_ADMIN_PASSWORD`/`SEED_ADMIN_NAME` from env (see `.env.example`). Idempotent by design, not by accident — checks `user` by email first (bare `db` client; `user` is a Better-Auth-generated table, deliberately not RLS-enabled, so there's no scope to go through): creates if absent, promotes to `role: "admin"` if present but not yet one, no-ops if already an admin. Verified live against the real dev DB, not just read: ran it once to create `ahmedbashir2028@gmail.com` as a real platform admin, then re-ran it and confirmed it correctly reported "already a platform admin" instead of erroring or duplicating.
- **The whole sign-in flow was verified live against the real running dev servers, not just unit-tested** — `apps/admin`'s dev server (`:3000`) and `apps/api`'s (`:8787`) both actually running, a real user signed up and signed in through the exact endpoints `authClient` calls, with the browser's `Origin` header set so CORS is genuinely exercised (not bypassed the way a bare non-browser request would be) — confirmed `access-control-allow-origin`/`access-control-allow-credentials` come back correctly, the session cookie authenticates a real protected route (`GET /profile`), and a wrong password is correctly rejected (401). Test data cleaned up via the real `DELETE /account` endpoint afterward.

## Row-Level Security

Defense-in-depth on top of app-level scoping, not a replacement for it — every route still has its own auth/permission checks. Applies to tables _we_ own and control every query for (currently `organization_billing`, `individual_billing`, and `profile`). Deliberately not applied to Better-Auth-generated tables (`user`, `session`, `member`, etc.) — Better Auth queries those internally via `drizzleAdapter`, and we don't control every query shape it issues; RLS there risks breaking login/session resolution on a library version bump for no real security gain (Better Auth's own session validation is already that trust boundary).

- **The app connects to Postgres as two different roles.** `DATABASE_URL` (owner role) is used only for migrations. `APP_DATABASE_URL` (a restricted `app_user` role, no `BYPASSRLS`) is what `packages/db/src/index.ts`'s `db` client actually uses at runtime — `packages/db/src/index.ts` throws at import time if `APP_DATABASE_URL` is unset, on purpose, rather than silently falling back to the owner role. **This split exists because Neon's default owner role has `BYPASSRLS` granted directly on the role** (not just table-owner exemption, which `FORCE ROW LEVEL SECURITY` would handle) — confirmed by querying `pg_roles.rolbypassrls` directly, not assumed. Any Postgres host's default/admin role should be treated with the same suspicion until checked.
- `packages/db/scripts/create-app-role.js` (run via `pnpm --filter @repo/db create-app-role`, needs `DATABASE_URL` + `APP_ROLE_PASSWORD` set) creates/updates this role: grants on all current tables, plus an `ALTER DEFAULT PRIVILEGES` rule so future tables are covered automatically — confirmed working for real when `individual_billing` was added and needed no manual re-grant. Re-run it only if you need to rotate the password.
- **Run this before the first `pnpm db:migrate` on a fresh database, not after.** `GRANT ... ON ALL TABLES` is a harmless no-op with zero tables present, and `ALTER DEFAULT PRIVILEGES` still covers every table a subsequent migration creates — but a migration that references `app_user` _by name_ (not just via an RLS policy's `current_setting(...)` check), like `0019_billing_events_immutability.sql`'s `REVOKE UPDATE, DELETE ON billing_events FROM app_user`, fails outright with "role app_user does not exist" if the role isn't already there. This broke CI (`.github/workflows/ci.yml` used to create the role _after_ migrating) precisely because 0019 was the first migration to do this — every earlier migration only ever checked `current_setting(...)` at query time, which tolerates the role not existing yet at migration time.
- Query an RLS-enabled table only through `withOrgScope(organizationId, callback)`, `withUserScope(userId, callback)`, or `withSystemScope(callback)` (`packages/db/src/index.ts`) — never the bare `db` client directly. All three wrap `db.transaction` and set a transaction-local session var (`set_config(..., true)`, bound-parameterized, not string-interpolated `SET LOCAL`) that the table's policy checks via `current_setting(...)`.
  - `withOrgScope` / `withUserScope` — for anything acting on behalf of a live user session that has a real `organizationId` / `userId` (e.g. `requireFeature` uses both). Two independent session variables (`app.current_org_id`, `app.current_user_id`), not one shared key — a query could in principle need both, though nothing does yet.
  - `withSystemScope` — bypasses scoping entirely, only for contexts trusted through a _different_ mechanism than a session (e.g. `billing.handlers.ts`'s webhook processing, trusted via Stripe's verified signature; some webhook events don't even carry an owner id to scope to). Never use this for anything reacting to a live user request.
- `.db.ts` functions for an RLS-enabled table take an explicit executor (`tx: DbExecutor`) as their first parameter instead of importing `db` directly — makes it impossible to accidentally query the table outside a chosen scope. `organization-billing.db.ts` / `individual-billing.db.ts` are the reference examples.
- The policy pattern (`organization_billing_isolation`, `individual_billing_isolation`) is `<owner_column> = current_setting('app.current_<owner>_id', true) OR current_setting('app.bypass_rls', true) = 'true'` — `current_setting(..., true)` returns `NULL` (not an error) when unset, so a query that goes through neither helper sees zero rows: fail closed, not fail open.
- **Any new RLS-enabled table needs both `ENABLE` and `FORCE ROW LEVEL SECURITY`, and a real test proving unscoped/wrong-scope access returns nothing** — a policy without `FORCE`, or with the `app_user` role somehow regaining `BYPASSRLS`, fails silently. Don't trust that RLS works because the migration ran; `billing.integration.test.ts`'s and `individual-billing.integration.test.ts`'s "Row-Level Security" describe blocks are the reference examples for how to prove it.
- **Renaming an RLS-enabled table needs a hand-written `RENAME TO` migration, not a `drizzle-kit generate` diff** — a plain rename would otherwise look like drop+recreate to drizzle-kit unless answered interactively (which breaks non-interactive/CI generation). After a hand-written rename migration, also update the corresponding `packages/db/migrations/meta/<n>_snapshot.json` by hand (rename the table key and all its internal name references) so drizzle-kit's own tracked state matches reality — otherwise the next `db:generate` prompts an interactive "created or renamed?" question. `0005_rename_billing_tables.sql` (and its matching hand-edited `0005_snapshot.json`) is the reference example.

## Environment & running things

- Package manager is **pnpm** — don't use npm/yarn.
- **`NODE_ENV` has exactly one source: `cross-env NODE_ENV=<mode>` in each `apps/api` script.** Never set inside a `.env.*` file — `cross-env` sets it before `--env-file` would load, and `--env-file` never overrides an already-set var, so a duplicate line there is inert. There is deliberately no `.env.production` file — production secrets come only from the hosting platform at deploy time.
- `.env.development`/`.env.test` hold the rest of local config, loaded via `tsx`/`node`'s native `--env-file`, no `dotenv`. Vitest's own CLI has no `--env-file` support (why `cross-env` exists at all rather than relying on `--env-file` uniformly) — `apps/api/vitest.setup.ts` calls `process.loadEnvFile()` to cover it.
- `apps/api/src/lib/response.ts`'s `isDev()` is the single place that reads `NODE_ENV` for error verbosity — don't re-derive "are we in dev" elsewhere.
- `pnpm dev` (root) runs all apps via Turborepo; `pnpm --filter @repo/api dev` runs just the API.
- `pnpm db:generate`/`pnpm db:migrate` wrap drizzle-kit, loading `.env.development` themselves. `DATABASE_URL` there points at a real Neon instance — live, not a placeholder. Think about destructive schema changes the way you would against a real staging DB.

## Production hardening

A handful of concurrency/load-bearing fixes, closed after a load-focused audit (not yet under any real traffic, but the gaps were real):

- **The Postgres pool's `max`/timeouts are explicit and env-driven** (`packages/db/src/index.ts`, `DB_POOL_MAX`/`DB_POOL_IDLE_TIMEOUT_MS`/`DB_POOL_CONNECTION_TIMEOUT_MS`, see `.env.example`) — node-postgres's own defaults are wrong for production: `max: 10` silently caps this whole app's concurrent DB-bound requests regardless of traffic, and `connectionTimeoutMillis: 0` means a request waiting for a free connection waits forever instead of failing with a clear error. `pool.on("error", ...)` is also required — pg's own docs warn an unhandled `'error'` event on an idle pooled client crashes the entire process (any Node `EventEmitter`'s unhandled `'error'` throws).
- **Graceful shutdown** (`apps/api/src/lib/graceful-shutdown.ts`, wired in `index.ts`) — `SIGTERM`/`SIGINT` stop the server accepting new connections, let in-flight requests finish, close the DB pool, then exit, instead of a deploy/scale-down signal killing the process mid-request. Force-exits after 10s regardless: `server.close()`'s callback only fires once every connection it's tracking has ended, but doesn't proactively close already-upgraded WebSocket connections — a client that just stays connected would otherwise hang shutdown forever.
- **The WebSocket dispatcher supports more than one connection per user** (`websocket-dispatcher.ts`) — `Map<string, Set<WSContext>>`, not `Map<string, WSContext>`. The single-value version had a real bug, not just a theoretical one: a second connection (a second tab/device) silently overwrote the first's registration, and closing the _first_ connection then deleted the _second_'s still-open entry from the map — a live socket that would never receive anything again. `NotificationDispatcher.removeClient` (`packages/core/src/notifications/types.ts`) now takes the specific client to remove, not just a `userId`, so it can tell connections apart. Regression-tested directly in `websocket.integration.test.ts` (two connections, close the first, assert the second still receives a message) — this reproduces with exactly one user and two tabs, it isn't a "100k users" scale issue.
- **Stripe checkout accepts a caller-supplied idempotency key** (`BillingGateway.createCheckoutSession`/`createIndividualCheckoutSession`'s optional `idempotencyKey` param, read from an `Idempotency-Key` request header in `billing.controller.ts`) — verified against the installed Stripe SDK's actual source (`RequestSender.js`'s `_defaultIdempotencyKey`) that it already auto-generates a fresh key per call when none is supplied; that only protects the SDK's _own_ internal network-retry, not a retried HTTP request to _our_ API, since a new inbound request looks identical to the server either way. A server-generated key would have added nothing beyond what the SDK already does. Optional and additive — callers that don't send the header get today's behavior unchanged.
- **`requirePermission` no longer calls `auth.api.hasPermission(...)`** — a genuinely redundant DB round-trip, not a caching shortcut. Traced Better Auth's actual source before changing this (`has-permission.mjs` → `permission.mjs`'s `hasPermissionFn` → `access.d.mts`'s `Role.authorize()`): the real permission check is a pure, synchronous, in-memory function on a `Role` object — the DB cost was entirely in re-deriving the session and re-fetching the member's role, both of which `injectUserContext` already resolved earlier in the exact same request (`userContext.roles`). `requirePermission` now calls the same `Role.authorize()` directly via `roles` (`packages/core/src/auth/permissions.ts`, now also the single source the `organization` plugin's own config uses, replacing a duplicated inline object). **This is not the same class of change as a cross-request cache** — it introduces zero staleness risk, since it reuses data fetched moments earlier in the same request rather than holding anything across requests. Session/role freshness for `injectUserContext` itself is untouched; don't extend this pattern to actually cache session/role data _across_ requests without treating that as the separate, real security-freshness tradeoff it would be.

## Email

`EmailSender` (`packages/core/src/email/types.ts`) is a transport, not a notification. `apps/api` registers the implementation at startup (`lib/auth-wiring.ts` → `modules/email/select-email-sender.ts`): Resend when `RESEND_API_KEY` is set, otherwise the console sender, except in production, which gets **no** sender. Same interface-in-core split as `BillingGateway`; see specs/email-and-account-recovery-plan.md.

- **Auth emails call `sendEmail` directly, never through notifications.** They carry one-time tokens, and notifications are persisted and shown in the in-app inbox. They also go to people with no account or an unverified email. A future email notification channel calls the same `EmailSender`.
- **`sendEmail` never rejects.** With no sender it warns and drops; a failing sender is logged by subject only, never the recipient or body, so tokens never reach the logs. A missing or broken provider can't break sign-up, invites or a reset request.
- **Better Auth hooks fire the send and return, never `await` it** (`packages/core/src/auth/emails.ts`). Better Auth 1.7.12 awaits all three hooks (`password.mjs`, `sign-up.mjs` / `email-verification.mjs`, `crud-invites.mjs`). Awaiting delivery in the reset hook makes a known address answer measurably slower than an unknown one. `email.integration.test.ts` proves it with a sender that never delivers.
- **Every link comes from config, never the request** (`packages/core/src/auth/urls.ts`):
  - reset → `${PORTAL_URL}/auth/reset-password?token=`;
  - invitation → `${PORTAL_URL}/auth/accept-invite?id=`, kept in sync with the portal's `acceptInvitePath`;
  - verification → Better Auth's own `/verify-email` URL, with its client-supplied `callbackURL` replaced by `${PORTAL_URL}/auth/email-verified`.

  `PORTAL_URL` and `BETTER_AUTH_URL` are checked once at startup, required and `https://` in production. Never fail per request: that would make known and unknown addresses answer differently.

- **`resend` is imported only in `modules/email/resend-email.sender.ts`.** Resend returns API errors instead of throwing, and the adapter turns them into rejections. The console sender prints links by design, which is why it's never picked in production.
- Templates are plain functions returning `{ subject, html, text }` (`packages/core/src/email/templates.ts`), always with a text part. They escape every interpolated value: org and inviter names are user-controlled and land in someone else's inbox.
- `requireEmailVerification` stays off; turning it on would lock out existing unverified accounts and needs its own rollout decision. Resending verification is rate-limited at 3/min (`rate-limit.ts`).

## API response shape

Every `apps/api` response — except `/health`, `/api/auth/**` (Better Auth's own client SDK expects its native shape), and `/billing/webhook` (Stripe only checks HTTP status) — uses one envelope via `apps/api/src/lib/response.ts`:

- Success: `success(c, data)` → `{ success: true, data }`.
- Failure: never hand-construct one. `throw new AppError(code, message, details?)` from `@repo/core` and let `app.onError()` (`apps/api/src/app.ts`) format it — preferred over calling `failure()` directly. `code` is one of `ErrorCode` in `packages/core/src/errors.ts` (`UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_ERROR`, `PAYLOAD_TOO_LARGE`, `PAYMENT_REQUIRED`, `INTERNAL_ERROR`) — add a new code there, not a bespoke string.
- `details` only ships when `isDev()` is true. Never put anything unsafe-for-production in `message` — it always ships.
- Unexpected exceptions are still caught by `app.onError` into the same envelope (`INTERNAL_ERROR`) — no route needs its own try/catch for shape consistency. That same branch calls `Sentry.captureException(err)` (`apps/api/src/instrument.ts`, gated behind optional `SENTRY_DSN`, no-op if unset) — only for genuinely unexpected errors, not `AppError`/`HTTPException`. Don't scatter `Sentry.captureException` calls elsewhere; this is the one centralized reporting point.

## Testing

Two patterns — use the cheaper one whenever it answers the question:

- **Pure unit** (e.g. `lib/response.test.ts`) — standalone `Hono` instance, driven by `testClient` from `hono/testing`, no real socket/DB. For anything not needing a real session/DB row.
- **Integration** (`*.integration.test.ts`) — import the real `app`, boot with `serve()` on a dedicated port, exercise with real HTTP/WS clients against the real database. Required when the thing under test is a security boundary or needs a real Better Auth session. Every integration test cleans up what it creates in `afterAll`, unconditionally.
- Both patterns exercise the real app/route/middleware code, never a re-implementation.
- **Run integration tests against the local Docker database** (`docker-compose.yml`, `pnpm test:db`; README's "Running the API's integration tests"). `apps/api/vitest.setup.ts` loads `.env.test` before `.env.development`, and `process.loadEnvFile` never overwrites a set variable, so `.env.test`'s database URLs win. Without a `.env.test`, tests fall back to the dev database. Tests still clean up after themselves either way: the container lives for many runs, and the dev-DB fallback is shared.
  - **`.env.test`'s `APP_DATABASE_URL` must be `app_user`, never `postgres`.** The superuser bypasses Row-Level Security, so every RLS test would pass without proving anything. `pnpm test:db` creates `app_user` before migrating, the same order as CI.
  - Integration files still run one at a time (`fileParallelism: false`): they share one database and fixed ports.

## apps/admin

Next.js 16 + shadcn/ui admin dashboard, vendored from the open-source `next-shadcn-dashboard-starter` template (MIT — `LICENSE` kept, credited in README) and adapted into this monorepo, not left as a bare clone.

- **Talks to `apps/api` as a plain external REST backend, not through Next's own `/api/*` route handlers.** The template's own AGENTS.md documents a BFF/proxy pattern (`service.ts` → `/api/` route handler → real backend) as one of several supported backend patterns — deliberately not used here. `apps/api` already owns CORS, cookies, and Better Auth session validation server-side; a Next.js proxy hop would add latency with nothing to hide. Each feature's `service.ts` calls `apps/api` directly through the typed `hc` client (`src/lib/api.ts`, see Type safety).
- **Auth is not routed through the template's generic `types.ts → service.ts → queries.ts` REST layer at all.** `src/lib/auth-client.ts` — `createAuthClient` (`better-auth/react`) pointed at `NEXT_PUBLIC_API_URL`, with `organizationClient()`/`adminClient()` plugins mirroring exactly what's registered server-side (`packages/core/src/auth/index.ts`) — a client plugin not registered on the server just 404s. Better Auth's client already has its own reactive `useSession()`/`signIn`/`signOut`; wrapping it in React Query on top would fight the grain. Browser calls carry the session cookie automatically (`credentials: "include"` is the client default); a server-side RSC prefetch of authenticated data would need to forward the incoming request's cookie header manually via `next/headers`'s `cookies()` — Next doesn't do this for you.
- **Form validation is Zod, UX-only — the server stays the actual authority.** E.g. `src/features/auth/schemas/sign-in.schema.ts` checks email format and non-empty password to fail fast before a network round-trip; it deliberately doesn't duplicate Better Auth's exact password-length rules. **A Zod field must never carry `.default(...)` when `useAppForm`'s `defaultValues` already supplies one** — TanStack Form's `validators.onSubmit` requires the schema's _input_ type to exactly match the form's value type, and `.default()` makes that field optional on input, which a real `defaultValues` value never is. Hit this directly: `rememberMe: z.boolean().default(true)` broke `next build`'s type-check while `defaultValues` already had `rememberMe: true`. Fixed by dropping `.default()`, not by loosening the form's types. Forms use TanStack Form via `useAppForm`/`useFormFields` (`src/components/ui/tanstack-form.tsx`) — see the `kiranism-shadcn-dashboard` skill for the full form/table/query conventions this template already establishes; follow those for anything not auth-specific.
- **The shared `TextField`/`FormTextField` (`src/components/forms/fields/text-field.tsx`) — not a feature-local one-off — is where icon affordances and password-visibility toggles live**, via an optional `icon` prop and automatic `InputGroup` layout for `type="password"`. A plain field with no icon and not `type="password"` renders the exact same bare `Input` markup as before — this is additive, not a rewrite of every text field's look. Built this way after first shipping a duplicate feature-local `EmailField`/`PasswordField` in `sign-in-view.tsx`, then being told directly to route the investment into the shared component instead so every future form gets it for free, not just this one. The shared `CheckboxField` (`checkbox-field.tsx`) had a real, separate a11y gap fixed at the same time: its `FieldLabel` had no `htmlFor` pointing at the checkbox's `id`, so clicking the label text did nothing — only the small checkbox hit target worked. Both are additive, backward-compatible fixes, not behavior changes for existing callers.
- **Removed from the template, via its own `scripts/cleanup.js` (then deleted once applied)**: Clerk (auth/orgs/billing — no drop-in replacement exists for its hosted `<SignIn>`/`<OrganizationProfile>`/`<PricingTable>` widgets, so profile/billing/workspaces/team/exclusive pages were deleted along with it, not stubbed), Sentry, kanban, chat, the forms/react-query/icons demo pages, and all themes but `vercel`. Removed by hand (not covered by the tool): the retail products demo — unrelated to this app's actual domain. **Kept**: `.agents/`/`.claude/` skill directories — genuine reference material for this exact codebase's own conventions, not template filler.
- **`eslint-config-next`'s bundled presets don't work with this repo's ESLint 10** — `apps/admin/eslint.config.mjs` is hand-built instead (`@next/eslint-plugin-next` directly + `eslint-plugin-react-hooks@7.1.1`, dialed down from its new React-Compiler-purity "recommended" rule set to just `rules-of-hooks`/`exhaustive-deps`). No `eslint-plugin-react`/`jsx-a11y`/`import` rules right now — `eslint-plugin-react`'s peer range doesn't include ESLint 10 yet and crashes at runtime (`context.getFilename is not a function`) if forced. Don't reintroduce `eslint-config-next`'s presets without re-checking this is fixed upstream first.
- **Has its own Vitest + jsdom + React Testing Library setup** (`vitest.config.ts`/`vitest.setup.ts`, `pnpm --filter @repo/admin test`) — separate from `apps/api`'s integration-test conventions above, since this is component-level, not real-server/real-DB. Mock only true I/O boundaries (`next/navigation`, `authClient.*` network calls) — everything else (Zod validation, form state, rendering) runs for real. `sign-in-view.test.tsx` is the reference example.
- **`src/proxy.ts` gates `/dashboard/**` on session-cookie presence** — `getSessionCookie(request)` from `better-auth/cookies`, Better Auth's own documented Next.js middleware pattern. No session → redirect to `/auth/sign-in`; has a session and hits `/auth/**` → redirect to `/dashboard/overview` (don't show the login form to someone already signed in). **This is a presence-only check, not real session validation** — no DB round trip is possible in middleware, so a stale or forged cookie value passes it. It only decides where to route the browser; `apps/api` is still the actual security boundary, independently re-validating the real session on every authenticated request it serves. Don't upgrade this to "real" auth checking in middleware without treating that as the separate, larger tradeoff (edge runtime, latency, DB access from middleware) it would be. `proxy.test.ts` is the reference example for testing it — mocks only `getSessionCookie`, exercises real `NextRequest`/path-matching logic.
- **The `next-best-practices` skill's file-conventions.md claims Next 16's `proxy.ts` needs `export const proxyConfig` instead of `config` — this is wrong, verified against the installed Next.js 16.2.6 source, and re-checked unchanged in 16.4.2, not assumed.** `next/dist/build/analysis/get-page-static-info.js`'s `validateMiddlewareProxyExports` only checks the _function_ export name (`middleware` vs `proxy`, matching the file's own name); the actual matcher config extraction (`extractExportedConstValue(ast, 'config')`, same function, called for both legacy `middleware.ts` and `proxy.ts`) is hardcoded to the literal string `'config'` — no code path anywhere in the installed package looks for `'proxyConfig'`. Only the function name changed in the middleware→proxy rename, not the config export. Keep `export const config = {...}` in `proxy.ts`; don't "fix" this per the skill without re-verifying against a real Next.js source release first.
- **`src/features/users/` is the real platform-employees feature, not the template's fake-data demo anymore** — `types.ts`/`service.ts`/`queries.ts`/`mutations.ts` call `authClient.admin.*` directly (no `apps/api` route, no Next.js `/api/*` route handler — both would be a needless hop, see the Platform admin section above). `service.ts`'s `unwrap()` helper normalizes Better Auth's `{ data, error }` contract (never throws) into thrown `Error`s so TanStack Query's error handling works the ordinary way — same pattern as `auth-client.ts`'s calls. Row types are Better Auth's own `UserWithRole` (`types.ts`), not a hand-written copy — same for the `staff` feature, which `nav-config.ts` links to (`/dashboard/users` is no longer in the nav). The old `app/api/users/**` route handlers and the fake `fakeUsers`/`generateRandomUserData` store are deleted; `src/constants/mock-api-users.ts` now only exports `delay`, still used by the overview dashboard's parallel-route pages (`@area_stats`/`@bar_stats`/`@pie_stats`/`@sales`) to simulate loading latency for their own separate mock chart data — don't delete `delay` along with the rest.
- **Import `@repo/core`'s auth pieces from a specific subpath, never the package root, in client-side code.** `packages/core/src/index.ts` re-exports everything including `./auth`, whose `index.ts` constructs a live `betterAuth()` instance at module-load time with a real `drizzleAdapter(db, ...)` Postgres connection — importing `@repo/core` or `@repo/core/auth` from browser code would bundle that DB-connecting code into the client. `packages/core/package.json` exports a dedicated side-effect-free `"./auth/platform-permissions"` subpath for exactly this reason; `auth-client.ts` imports `platformAccessControl`/`platformRoles` from there, nothing else. Add further subpaths the same way if client code ever needs another auth-adjacent piece that isn't safe to pull in via the barrel.
- `.env.local` (gitignored, matches root's `.env.*` convention) holds `NEXT_PUBLIC_API_URL` — see `apps/admin/.env.example`.
- **`src/lib/api.ts`'s `api` (`createApiClient<AppType>`, `@repo/shared/hc-client`) is the one place every non-auth feature calls `apps/api`** — same file in `apps/portal`. It always sends `credentials: "include"`, and a call made without `NEXT_PUBLIC_API_URL` fails with an error naming it (checked per call, not at import, so CI's env-less `next build` still works). Pass per-call headers as `{ headers }` (a plain object — e.g. a server-side prefetch forwarding `{ Cookie }`); never put `headers` in the client's `init`, since `hc` spreads `init` after the headers it builds and would replace them. `unwrap()` (`@repo/shared/api-response`) turns the envelope into `data` or an `ApiError` carrying `code`/`message`/`status`/`details` — callers branch on `.code`; a non-envelope response (a proxy's error page, an empty 2xx) becomes `"HTTP_ERROR"`. `ErrorCode` is derived from `@repo/core/errors`, not a copy. Doesn't apply to Better Auth calls — `auth-client.ts` has its own `{ data, error }` contract. Each feature's `api/service.test.ts` pins its exact requests, mocking only global `fetch`.

## apps/portal

Customer-facing Next.js app (B2B org members + B2C individuals), same stack and conventions as `apps/admin` — see `specs/customer-portal-plan.md` for the design. Rules specific to it:

- **`organizationClient()` gets the same `ac`/`roles` as the server** (`@repo/core/auth/permissions`, a side-effect-free subpath) so permission checks type-check. No `adminClient` — this audience is never platform staff.
- **"Can this user do X?" always goes through the shared `roles` map, never by comparing role names** — either the server (`authClient.organization.hasPermission`, as billing does) or locally via `Role.authorize()` on the caller's role from the live member list (team, `canManageTeam` — same check apps/api's `requirePermission` runs). Prefer the local check when the member list is already loaded: `hasPermission` is a network call, and every `/organization/*` call also triggers a full-organization refetch in Better Auth's client. Either way it's UX gating only; the server enforces regardless.
- **Switch organizations only through `src/hooks/use-switch-organization.ts`**, never by calling `organization.setActive` directly — the hook also invalidates every cached query (the spec's "Org-switch cache invalidation"), so billing can't keep showing the previous org's data. Used by the nav's `OrganizationSwitcher` and `/team`'s chooser.
- **A `DropdownMenuLabel` must sit inside a `DropdownMenuGroup`** — Base UI throws `MenuGroupContext is missing` the moment the menu opens otherwise (this crashed the portal's account menu from 0.25 to 0.28 unnoticed). Any menu with a label needs a test that actually opens it; rendering the trigger alone proves nothing.
- **Better Auth doesn't set an active organization at sign-in.** An org member on a fresh session has none until one is chosen (`organization.setActive`) — so "no active organization" must not be read as "individual account". `/team` offers the user's organizations in that case, and the nav shows Team to anyone who belongs to one.
- **Organization data comes from Better Auth's reactive hooks, not React Query.** `useActiveOrganization()` (members, invitations) refetches itself after every `/organization/*` call — verified in the installed `client.mjs` `atomListeners` — so team changes need no manual invalidation. React Query is for `apps/api` data (billing), with organization-scoped data keyed by `organizationId` so an org switch can never show the previous org's cache.
- **Better Auth errors keep their `code`** (`src/lib/auth-action.ts`'s `AuthActionError`, shared by the team and organization features' services), and the UI maps known codes (`INVITATION_LIMIT_REACHED`, `ORGANIZATION_MEMBERSHIP_LIMIT_REACHED`, …) to plain-language messages instead of showing raw ones.
- **`?redirect=` on sign-in/sign-up is untrusted input** — always pass it through `src/lib/safe-redirect.ts`'s `safeRedirectPath` (same-site paths only), never to `router.push` directly, or it becomes an open redirect.
- **Invitations are emailed and shareable as links**: `/auth/accept-invite?id=…`. Better Auth only reveals an invitation to a signed-in user whose email matches it, so that page sends signed-out visitors through sign-in/sign-up and back.
- **`proxy.ts` lets signed-in users reach three `/auth` pages** (`AUTH_PATHS_OPEN_WHEN_SIGNED_IN`):
  - `accept-invite`, for accepting an invite to a second org;
  - `reset-password`, where the emailed token, not the session, decides the account;
  - `email-verified`, because verifying signs the user in.

  Every other `/auth` page bounces a signed-in user to `/profile`. A new emailed-link landing page belongs in that list, with a proxy test.

- **Known upstream limit:** with `membershipLimit` set to a function (our seat limits), Better Auth's `get-full-organization` caps its member→user lookup at 100, so an uncapped organization past 100 members would fail to load its member list. No current plan allows that many (largest cap: 50); revisit before offering one that does.

## CI/CD

- **Pre-commit** (Husky + lint-staged, `.husky/pre-commit`): staged `.ts`/`.tsx` get `eslint --fix` + `prettier --write`; staged `.json`/`.md`/`.yaml` get `prettier --write`. Runs automatically, don't bypass with `--no-verify`.
- **CI** (`.github/workflows/ci.yml`, on PR/push to `main`): `quality` job (production dependency audit, format check, lint, typecheck, build) must pass before `test` job runs (spins up a real `postgres:16` service, writes its own `.env.development`, creates the restricted `app_user` role, _then_ runs `pnpm db:migrate` and `pnpm test`). The role-creation step must come before `db:migrate` — see the Row-Level Security section's note on why order matters here.
- CI's `.env.development` sets a fake `STRIPE_WEBHOOK_SECRET` (so self-signed webhook tests still work) but deliberately has no `STRIPE_SECRET_KEY`/`STRIPE_PRICE_STARTER` — this is _why_ `billing.integration.test.ts`'s real-Stripe-checkout test uses `it.skipIf(!process.env.STRIPE_PRICE_STARTER)`. **Any new test needing a real third-party credential must skip gracefully the same way, or CI breaks.**
- Adding a required env var for tests → add it to ci.yml's "Create test environment file" step too, or CI's `test` job fails even though local tests pass.
- **CI runs `pnpm --filter @repo/api seed:subscription-plans` after `db:migrate`, before `pnpm test`.** `0017_seed_default_subscription_plans.sql` only seeds the two free-tier defaults (`free`/`individual_free`) — enough for entitlement/seat-limit fallbacks, not enough for `entitlement.integration.test.ts`'s "upgrade to a plan with the feature" cases, which need the paid tiers (`growth`, `individual_pro`, `starter`) `apps/api/scripts/seed-subscription-plans.ts` adds. Those paid-tier rows previously only ever existed in local dev DBs via a manual one-off run of that script — CI's ephemeral database never had them, which silently degraded every "upgrade" case to `fallbackEntitlements` (402) until this step was added. Any new plan-gated test needing a specific paid tier must have its row added to that script's `seedPlans` list, not created ad hoc in the test itself.

## Dependency security

See `specs/security-upgrades-plan.md` for the full reasoning.

- **Upgrade to the smallest safe version**: the newest patch of the release line that fixes the advisory, not the newest major. E.g. Vite 6.4.x rather than 8, and `@vitejs/plugin-react` 4.x, which accepts Vite 6.
- **Wait 3 days before installing a new release.** `pnpm-workspace.yaml`'s `minimumReleaseAge: 4320` (minutes) makes pnpm refuse anything newer (`ERR_PNPM_NO_MATURE_MATCHING_VERSION`); a hijacked maintainer's release is usually pulled within days. For an emergency patch, add it to `minimumReleaseAgeExclude` with a comment, and remove it afterwards. Fetch tools with `pnpm exec`/`pnpm dlx`, not `npx`: npm doesn't enforce this rule.
- **CI fails on any high or critical advisory in a production dependency** (`pnpm audit --prod --audit-level high`, `quality` job). Fix it with a real upgrade. Refreshing a vulnerable transitive dependency inside its parent's range (`pnpm update -r <pkg>`) beats `pnpm.overrides`, which needs sign-off. Never silence an advisory. Dependabot (`.github/dependabot.yml`) opens security-update PRs only, no routine bumps.
- **`hono` and `better-auth` are pinned to one exact version in every package that uses them.** Bump each everywhere at once. `@better-auth/*` packages move with `better-auth`.
- **Re-verify after every Better Auth bump.** Every claim in this file about Better Auth's source (`has-permission.mjs`, `routes.mjs`, `crud-invites.mjs`/`crud-members.mjs`, the client `atomListeners`, the 100-member cap, `afterCreateOrganization`) was last re-verified against **1.7.12**. Check them again on the next bump, and run the duplicate-account query from its upgrade guide first.
